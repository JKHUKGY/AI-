# Docs Skill Builder (中文版)

> 这是 [SKILL.md](SKILL.md) 的中文翻译, 只供人阅读。**英文版是权威版本**, 两者不一致时以英文版为准, 并把这份翻译改过来。
>
> 这条约定只写在这里。`SKILL.md` 是正式出版物, 也是真正被 Claude Code 加载进上下文的那份, 所以它里面不提翻译的存在 —— 那对 agent 执行任务没有任何用处。维护责任是单向的: 改了 `SKILL.md` 就回来同步这份, 反过来不成立。

产出一个 `xxx-docs` skill: 一个按需从厂商官方文档里找答案的 lazy loader。调用方式:

```
/docs-skill-builder build .claude/skills/databricks-docs for https://docs.databricks.com
/docs-skill-builder check  .claude/skills/databricks-docs
```

把 `$ARGUMENTS` 解析成 **模式** (`build`, 默认; 或 `check`)、**目标路径**、**对象** (一个 URL 或产品名), 以及**附加说明**。附加说明是要求, 不是建议 —— 要么照做, 要么明说为什么没做。

整件事只有一个问题: **用最省的方式找到对的页面, 再用最省的方式读它。** 其余全部由测量结果推导出来。

## 贯穿全程的原则

这几条决定所有的边界情况:

- **测量, 不假设。** 产出 skill 里的每个数字都来自探测报告。测不到的, 就不要写。
- **描述契约, 不物化清单。** 能用一条规则("URL 后面加 `.md`")表达的, 绝不落成一份抓下来的清单。清单是第二个真相来源, 只会越来越错。
- **用站点自己的层级。** 它的分节和落地页是厂商在维护的, 永远最新。自己发明一套分类是负债。
- **用推理换召回, 不用产物换召回。** 查询时做同义词扩展和分节兜底, 好过预先富化、然后过期的索引。
- **爬虫是下下策**, 必须满足 catalog 第 6 节的准入条件。
- **做个有礼貌的客户端。** 探测脚本硬上限约 28 个请求并带节流, 不要循环调用。构建过程绝不批量抓页面。

## Phase 1 —— Discovery

Discovery 是**你的**工作, 不是脚本的。分两半, 同时进行。

### 1a. 机械的那一半 —— 跑探测脚本

```bash
python3 ${CLAUDE_SKILL_DIR}/scripts/probe_docs_source.py \
    --domain <docs-url> --generated_at $(date +%F) --json_out /tmp/<name>-facts.json
```

完整参数看 `scripts/probe_docs_source.py --help`。它做的事: 遍历一个**约定俗成的确定性位置**的注册表 —— `llms.txt`、`llms-full.txt`、`.well-known/llms.txt`, 在目标路径**和它的每一级父路径**上各试一遍 —— 然后对找到的东西做统计, 拿一个真实叶子页面试 6 种纯文本约定, 并数 sitemap 的 URL 数。它打印一份报告; 加 `--json_out` 会把同样的数据以 dataclass 结构输出成 JSON。

**必须清楚它到底帮你省了什么。** 它是在替代"你手工发二十个 WebFetch 然后肉眼数"这件事, 仅此而已。具体地说:

- 它只认识注册表里那些位置。**一个把索引放在非常规位置的站点, 探测结果会是空的, 而这不能证明索引不存在。**
- 它不判断质量 —— 它数描述有几个词, 但不读描述写得好不好。
- 它不做决策。`conclusion` 那一段是它按自己的阈值做的确定性推断, 目的是给你一个带类型的起点。要对着 catalog 确认; 站点特殊时就推翻它, 并说明理由。

当 conclusion 里 `needs_manual_discovery: true`, 意思是机械的那一半跑完了、什么都没找到。**不要据此就回答"这个站没有索引"。** 老老实实去做 1b。

### 1b. 人的那一半 —— 搜索和判断

这一半永远要做, 哪怕探测脚本已经找到东西了:

- **联网搜索索引位置。** `llms.txt` 的位置没有标准: 搜 `"<产品> llms.txt"`、`"<产品> docs for LLMs"`, 以及厂商自己的 docs-for-AI / 开发者页面。找到的用 `--extra_index_url <url>` 喂回去重跑一次。
- **找开源文档仓库。** 很多厂商把文档以 markdown 发在 GitHub 上。仓库能给出完整文件清单加原始 markdown, 经常比 llms.txt 和 sitemap 都好。要确认它跟已发布版本一致, 而不是超前于线上。
- **看厂商是不是已经自己发了东西** —— 官方 MCP server、Claude Code 插件、文档搜索 API。有的话要报告: 这个 skill 可能因此变得多余, 也可能是互补的(手写最佳实践 vs 权威原文)。让用户决定, 不要默默造一个重复的轮子。
- **如果探测是空的, 去看看真实的文档站。** 它自己的搜索是怎么实现的? 背后有没有 JSON 接口? 有没有打印版/原始版视图? 这些是注册表猜不到的真实机制。

如果你发现了注册表不认识的新约定, **就加进去** —— 在 `REGISTRY.index_rules` 或 `REGISTRY.content_rules` 里加一条, 下次构建就白捡。

## Phase 2 —— 决策

现在去读 [references/mechanism-catalog.md](references/mechanism-catalog.md), 套用它的决策表。选出**索引档位 (T0–T5)** 和**正文档位 (C0–C2)**, 把探测脚本的 `conclusion` 当起点而不是判决, 并记下你否决了哪个方案、为什么。

然后给用户发**一条**汇总消息: 关键数字、选定的设计、一句话的取舍、厂商已有的东西、以及需要定的范围问题。只有当答案真会改变构建结果时才用 AskUserQuestion —— 比如两个档位在测量误差之内, 或者要不要包含体量很大的 API reference 分节。如果事实已经足够决定, 附加说明也覆盖了范围问题, 那就直接说你要怎么做然后开工。

两个容易判错的地方:

- **看着舒服但覆盖率很低的索引。** 看 `coverage`。Databricks 的索引 47 KB、98% 有散文描述, 但只覆盖全站 4.5% —— 必须叠加 T4, 否则这个 skill 会自信地漏掉几乎所有内容。
- **只有 HTML 的正文。** 要用 WebFetch 而不是 curl。它会先把 HTML 转成 markdown 再进上下文; 原始页面可能 50 KB 到 900 KB。

## Phase 3 —— 产出

按 [references/skill-template.md](references/skill-template.md) 里的文件清单、`docs-source.json` schema 和 SKILL.md 结构来写。另外:

- 把 `assets/docs_query.py` **原样复制**到 `<target>/scripts/`。不要 fork —— 站点差异属于 `docs-source.json`。如果某个站点真的没法用那个配置表达, 优先扩展配置 schema 而不是写专用脚本, 并且要说明。
- **T0 档完全不生成 `scripts/`。** 索引直接进上下文的 skill 不需要代码。
- 给 `references/mechanism.md` 写下第一条日志: 这个站是怎么被读取的、为什么选这个设计、被淘汰的备选是什么、什么情况下该推翻它、以及重建时必须保留的手写资产。从此这个文件只追加不改写 —— 条目格式和字数预算见模板。
- 遵循本项目约定: `VERSION` (从 `0.1.1` 开始) 和 `CHANGELOG.md`。
- **三对翻译一个都不能少**: `SKILL.md`、`README.md`、`references/mechanism.md` 各自配一份 `-cn.md`, 同一轮里一起写完, 英文为准。英文版里绝不提翻译的存在, 这条约定只写在 `-cn.md` 里。所有档位都要求如此。
- `description` 要写得能被触发: 把产品名和真实的顶层领域(取自索引自己的分节名)放在最前面。如果用户用中文工作, 补上中文触发词 —— 索引里一个中文字都没有, 所以这是纯手写的, 必须在 `mechanism.md` 里标记为"重建时须保留"。

## Phase 4 —— 验收测试(不可跳过)

先证明这个 skill 根本加载得起来:

```bash
python3 -c "import sys,yaml; d=yaml.safe_load(open(sys.argv[1]).read().split('---',2)[1]); print({k:type(v).__name__ for k,v in d.items()})" <target>/SKILL.md
```

应该得到四个 `str` 字段。这一步放在最前面, 是因为 frontmatter 解析失败**不会报错** —— skill 会以
**空 metadata** 加载, 于是永远不会被触发, 那么下面每一项测试量的都是一个 agent 已经找不到的 skill。
本该是 `str` 的地方出现 `list`, 说明 `[…]` 没加引号; 见模板里 frontmatter 那一节。

然后跑产出 skill 自己的命令, 报告真实数字。按 catalog 第 7 节:

1. 一个简单查询, 关键词直接出现在标题里。
2. **一个词汇错配查询** —— 目标页面的标题里**没有**那个显而易见的搜索词。这才是关键测试; 这类 skill 就是这么失败的。
3. 一个非英文查询, 确认"先翻译"这条规则真的写下来了而且有效。
4. 一次正文抓取, 报告实测字节数。

如果第 2 项只有靠加载整个索引才能通过, 说明档位选错了 —— 回到 Phase 2。要报告实测成本, 不要宣称一个你没跑过的通过。

## `check` 模式

对已存在于 `<target-path>` 的 skill: 读它 `references/mechanism.md` 的**最顶上那条**, 对着记录里的索引 URL 重跑探测, 把事实和这个基线做 diff。报告:

- **索引搬家或死了**(跳转、404、登录墙)→ skill 已经坏了, 重建。
- **结构漂移**(分节改名、体积大幅变化、描述覆盖率跨过了档位阈值)→ 档位可能不再合适, 说清楚往哪个方向漂了。
- **正文契约变了**(`.md` 孪生页出现或消失)→ 通常意味着一大笔 token 的得失; 光是 C1→C0 就值得重建。
- **什么都没变** → 直说没变。no-op 是个好结果。

无论哪种情况都要重跑 Phase 4 的测试 —— skill 可能在事实没变的情况下腐烂, 而词汇错配那一项就是用来抓这个的。

然后**往 `references/mechanism.md` (以及它的翻译) 追加一条**, 记录这次 check 查到了什么 —— 哪怕答案是"什么都没变"。一次不留痕迹的 check 和一次根本没跑过的 check 是分不出来的。无变化的条目控制在 200 词以内, 并且**不要重述机制** —— 它下面那条仍然有效。

## 硬性规则

- **探测脚本是 discovery 的补充, 不是 discovery 本身。** 探测为空意味着"再搜仔细点", 绝不意味着"这个站没有索引"。
- **绝不手写数字进产出的 skill。** 数字要么来自探测报告, 要么就不出现。
- **绝不把正文提交进仓库。** 正文永远实时抓; 它变得最快。
- **绝不留占位符。** 模板里的 `<…>` 一个都不许进入产出。
- **绝不交付没有解析过的 frontmatter。** `argument-hint` 要加引号; 裸的 `[…]` 在 YAML 里是序列, 不是字符串。解析不了的 frontmatter 不会失败, 而是以空 metadata 加载, 于是这个 skill 就无声地变得永远触发不了 —— 在 Phase 4 里验证它, 不要靠肉眼看。
- **绝不改写 `mechanism.md` 里已有的条目。** 追加一条新的。这个日志的价值就在于它记录了当时相信什么、以及后来为什么变了。
- **绝不落下翻译。** `SKILL.md`、`README.md`、`references/mechanism.md` 都要连同各自的 `-cn.md` 在同一轮里更新。过期的翻译比没有翻译更糟 —— 它看起来像是最新的。
- **说清楚你跳过了什么。** 探测撞到预算上限、某个分节被排除、某项测试没跑 —— 都要说。默默省略会被读成"已覆盖"。
- **每个站每次构建只跑一次探测。** 需要更多请求就带着理由把 `--request_budget` 调大一次, 不要循环调用脚本。
