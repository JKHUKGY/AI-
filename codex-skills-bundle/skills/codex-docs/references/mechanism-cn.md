# codex-docs — 机制日志

这个 Skill 用什么方式读 OpenAI Codex 的官方文档, 以及为什么这么设计。最新的条目在最上面, 顶部那条
描述的就是当前的机制。条目只追加, 不改写。

## 2026-07-30 — 补录(reconstruction)

**结论。** 这一条是**倒推补录的, 不是实测**。这个 Skill 早于「机制日志」这项要求, 交付时就没有;
而且 owner 明确要求写这个文件时不要重新探测、不要更新它。下面的内容全部是从已交付的 `SKILL.md`、
`README-cn.md`、`CHANGELOG.md` 里还原出来的; 其中每一个数字都来自 2026-07-29 那次修复, 今天**没有**
重新核实。这里也没有任何本地产物可供测量, 所以和 `antigravity-docs` 不同, 这一条里没有任何今天新测
的数据。下一次真正的 `check` 必须跑 probe, 并追加一条有实测支撑的条目。

**这个站点是怎么读的。** 索引是上一级的 `https://developers.openai.com/llms.txt` —— 大约 840 行,
横跨 OpenAI 好几条互不相关的产品线, 按 `## <产品线> — <主题>` 分组, 每条仍是
`- [Title](URL): description` 的老格式。Skill 收窄到两族: `## Codex — <主题>` 和
`## Plugins — <主题>`, 然后把这两族的条目**一次性全部**载入并在其中搜索; 按主题的分组只是页面的排版
方式, 不构成进一步预筛的理由。当时记录的数字: Codex 条目约 137 条, 其中约 132 条可达。正文页是 `.md`
孪生页, 但要拿到它需要两次调用: `developers.openai.com/codex/<slug>.md` 会 308 跳到
`learn.chatgpt.com/docs/<slug>.md`, 而 WebFetch 不跟随跨域名跳转 —— 它会把跳转目标返回给你。所以第
一次调用是为了知道跳到哪, 第二次才真正读到页面; 这一对算作 9 页上限里的一页, 引用时写
`learn.chatgpt.com` 那个地址。`developers.openai.com/plugins/<path>.md` 下面的插件开发页是例外,
直连可达。

**为什么是这个设计。** 索引分层 **T1**(按分节路由), 内容分层 **C0**(纯文本 `.md` 孪生页)。选 T1
而不是 T0, 是因为这份 hub 索引并不是 Codex 的索引: 它大部分内容是 OpenAI API、Ads、Workspace
Agents、Agentic Commerce, 整份载入等于把大半预算花在范围外的东西上。而 `## Codex —` / `## Plugins —`
这套分组是官方自己的层级, 正是 catalog 推荐的那种路由 —— 上游维护、永远是最新的、本地什么都不用发明。
这里有一个刻意的界限: 路由只做到「产品线」这一层, 进了 Codex 和 Plugins 之内就全部扁平载入, 因为再
按主题标题收窄等于重新引入一次盲目路由, 而省下的那点开销不值得。

**为什么不用那个看起来最顺理成章的索引。** `https://developers.openai.com/codex/llms.txt` 已经死了:
旧域名上一整套 308 规则会把它一并改写到 `https://learn.chatgpt.com/docs/llms.txt`, 而那个地址返回
404。`codex/llms-full.txt` 同理。开发者站自己的根索引至今仍然挂着那个坏掉的 `codex/llms.txt` 链接,
照着走就是死路。新站也没有自己的 `llms.txt`, 只有一份不带描述的 `sitemap-index.xml` —— 用它会把这个
Skill 降到 T3 并彻底毁掉「按描述分诊」。这就是被迫上移到 hub 索引的原因。

**什么情况下这个判断会被推翻。** `learn.chatgpt.com` 发布自己的、带描述的 `llms.txt` → 索引直接改指
过去, 那套两次调用的跳转舞蹈可以整个扔掉, 这是眼下能拿到的最大一笔简化。308 跳转在迁移稳定后被撤掉 →
每页从两次调用变成一次, 抓取成本减半。hub 改名或重构 `## Codex —` 这些分节标题 → 第 1 步的 prompt
就匹配不上了, Skill 会在索引这一步整个失灵, 这正是 2026-07-29 那次故障的形态。hub 索引大到不适合再
整段读进上下文 → 改用 T2, 由脚本去搜索缓存下来的索引, 而不是 WebFetch 整节。

**重建时必须保留的东西。** 那套两次调用的跳转流程, 以及「一对算一页」这条规则 —— 任何索引里都没有写
它, 而没有它, agent 会把 `REDIRECT DETECTED` 当成报错。禁止自己拼 `learn.chatgpt.com` URL 这条规则,
它之所以存在, 是因为新旧 slug 不是简单换域名(`codex/skills.md` → `docs/build-skills.md`,
`codex/config-reference.md` → `docs/config-file/config-reference.md`)。关于「约 5 条索引条目在上游
就已失效、跳转之后仍然 404」的说明, 有了它 agent 才会把那些当作页面不存在, 而不是去手工修 slug。还有
**按产品线定义范围**这一点 —— `## Codex —` 和 `## Plugins —` 两族, 无论它们当前落在哪个域名 ——
而不是绑死某个 URL 前缀, 这正是下次再搬家时 Skill 不至于整个失效的原因。

**验收测试。** 没有跑。这一轮是在「明确不更新」的前提下补文件, 声称测试通过就等于声称跑过一个从未执行
的测试。特别是约 137 / 约 132 这两个条目数和那 5 条失效条目, 都是继承来的数字, 不是今天的。
