# antigravity-docs — mechanism log

How this skill reads Google Antigravity's documentation, and why. Newest entry first; the top
entry describes the current mechanism. Entries are appended, never rewritten.

## 2026-07-31 — build

**Verdict.** The defect recorded below is fixed. The mechanism is unchanged — still T5 against a
local manifest, still C1 content — but the manifest's description column now carries real text
for the first time, so triage has two working signals instead of one.

**What moved.** `antigravity-docs-index-builder` 0.2.2 replaced the dead
`template-content-paragraph` selector with the first substantial `<p>` after the body's `<h1>`,
and added a `Scrape coverage` report so a selector that stops matching can no longer degrade the
manifest silently. Manifest regenerated with `--force`: 81 pages (no pages added or removed),
21,934 B → 33,005 B, coverage **81/81 on section, title, and description**, no warning.
Boilerplate descriptions went from 81/81 to **0/81**; description length from a median of 3
words (max 6) to a median of 21 (max 48). Raw HTML entities in titles and breadcrumbs are also
gone — `clean()` now unescapes and no longer welds words together across stripped tags.

**Acceptance tests, run against the old and new manifests side by side.** Easy lookup `hooks?`:
2 → 5 entries. The vocabulary-mismatch cases are where the fix shows, since these are words that
appear in no title and no breadcrumb: `isolation` 0 → 1 (`cli/sandbox`), `parallel` 0 → 2
(`subagents`, `cli/subagents`), `open standard` 0 → 6 (`mcp`, `skills`, `cli/mcp`, `sdk/mcp`, …).
Two honest negatives: `12,000` (a limit stated in the body of `rules-workflows`) matches nothing
in either manifest — the index carries lead paragraphs, not full text, and that is by design; and
the non-English query `钩子` matches nothing in either, which is expected for an English index but
matters more here than it looks — see below.

**Newly visible gap, not fixed.** `SKILL.md` has no recall-escalation ladder: step 2 goes
straight from "nothing in the manifest obviously matches" to "say so". There is no instruction to
widen with synonyms, and none to translate a non-English query into English first. The `钩子` → 0
result above is exactly the silent failure that ladder exists to prevent, and the sibling
`claude-code-docs` grew one in its 0.2.0 for the same measured reason. Left alone here because
this pass was scoped to the manifest; it is the strongest remaining improvement available to this
skill.

## 2026-07-30 — reconstruction

**Verdict.** This entry is a **reconstruction, not a measurement.** The skill predates the
mechanism-log requirement and shipped without one, and the owner explicitly asked that the
skill not be re-probed or updated as part of writing this file. So the design below is
recovered from the shipped `SKILL.md`, `README-cn.md`, and `CHANGELOG.md`, and every live-site
number in it is inherited from the 0.2.1/0.2.2 work of 2026-07-25 and 2026-07-29 rather than
re-verified today. The only figures measured for this entry are the ones read out of the
committed manifest, which needs no network. The next real `check` must run the probe and
append a properly measured entry.

**How the site is read.** The index is **local**: `references/docs-manifest.json`, 21,934 B,
generated by the separate `antigravity-docs-index-builder` skill. The docs skill `Read`s it —
it does not fetch `llms.txt` and does not crawl. The file carries `_meta` (generation date,
source `llms.txt` SHA-256, `content_url_template`, page count) plus 81 `pages`, each
`{section, slug, title, description, content_url}`. `section` is a full breadcrumb path
(`Antigravity 2.0 / Customizations / Skills`) and is unique per page — all 81 values are
distinct, so it is a per-page label, not a grouping to route through. Content is the doc page
itself: `content_url` is `https://antigravity.google/docs/<slug>`, WebFetched directly, 1–3
pages per batch to a cap of 9. Since 0.2.1 the site is a server-rendered Astro app; before
that it was a client-rendered SPA whose page URLs returned an empty shell, which is why 0.1.1
fetched a separate `/assets/docs/….md` twin. That twin no longer exists. The server also
gzips unconditionally, ignoring `Accept-Encoding: identity`, so any manual `curl` check needs
`--compressed` or it returns what looks like binary garbage.

**Why this design.** Index tier **T5** (pre-built manifest), content tier **C1** (HTML only,
WebFetch never curl). T5 is the catalog's last resort and is justified here on one ground:
`antigravity.google/llms.txt` describes each page as "Learn about X", so triage-by-description
cannot work at all from the vendor index. The manifest is the sanctioned way to buy real
descriptions, and it ships with a rebuild path (`/antigravity-docs-index-builder`) rather than
being hand-patched. C1 follows from the pages being HTML: WebFetch reduces them to markdown
before anything reaches context.

**Known defect — one of the two triage signals is empty, traced to a stale regex.** Measured in
the committed manifest: **all 81 descriptions still match `Learn about <X>.`**, median 3 words,
longest 6 — identical to the `llms.txt` fallback. Traced to the source the same day: the
builder's `DESC_RE` looks for `<div class="caption template-content-paragraph">`, and that class
**appears zero times** in the current page HTML (checked against a live fetch of
`/docs/rules-workflows`); the lead paragraph is now a plain `<p>` immediately after the `<h1>`.
The other two scrapes are unaffected — `breadcrumb-list` and `<h1>` both still match, which is
why the manifest's breadcrumbs are correct and fine-grained. The failure is silent because
`build_manifest.py` only records a fallback in `scrape_failures` when `fetch()` raises; a regex
that matches nothing falls back with no warning at all, so the build reports success.

**This does not invalidate T5.** The breadcrumb alone is a large gain over the vendor index:
`llms.txt` offers 9 coarse `###` groups (Home, Antigravity 2.0, Antigravity CLI, SDK, IDE,
Migration, Enterprise, Plans, FAQ), while the manifest carries per-page paths such as
`Antigravity 2.0 / Customizations / Skills` and `Antigravity CLI / Commands / Resume (/resume)`.
Triage on title plus breadcrumb works, and the skill is functional. What is lost is the second,
independent signal — the one that would carry a query whose wording matches neither the title
nor the breadcrumb. Left in place per the no-update instruction; the fix is a one-regex change
in `antigravity-docs-index-builder`, not here, and the silent-fallback behaviour is worth fixing
alongside it since it is what let this go unnoticed.

**What would overturn it.** Real scraped descriptions landing in the manifest → T5 becomes
fully justified as documented. Antigravity publishing an `llms.txt` with usable descriptions →
drop the manifest and the builder skill entirely, move to T0 or T1 against the live index, a
large maintenance win. `.md` twins appearing at page URLs → C1 to C0. The site reverting to
client-side rendering → C1 breaks outright and the asset-twin workaround comes back. A 404 on
any `content_url` → the manifest is stale, not the URL wrong; rebuild rather than guess.

**Rebuild must preserve.** The "Why this skill works differently from claude-code-docs /
codex-docs" section of `SKILL.md` — it is the only place the T5 choice is explained to the
agent at read time. The pointer to `/antigravity-docs-index-builder` as the repair path for a
stale manifest, which is what stops the agent inventing slugs. The gzip trap written up in the
README's section 6: it is not discoverable from the docs site and costs an hour to rediscover.

**Acceptance tests.** Not run. This pass was a file backfill under an explicit no-update
instruction; claiming a pass would be claiming a test that never executed.
