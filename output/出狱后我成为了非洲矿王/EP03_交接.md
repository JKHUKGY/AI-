#### 出图实测参数（**这三条是这次踩出来的，别退回默认值**）

1. **`--timeout` 必须放大到 600。** 默认 240 秒对关键帧 job 完全不够——关键帧带
   2-4 张参考图、提示词 700-900 字，单张实测要 **8-12 分钟**。用默认值的后果不是
   "慢一点"：`run_task()` 超时后会**自动重试一次**，于是每张废图烧掉 2×240s=8 分钟
   且什么都不产出。第一轮用默认值跑了 12 分钟只落地 4 张，就是这个原因。
2. **`python3 -u` 不能省。** 不加 `-u` 时 stdout 被缓冲，日志文件一直是空的，
   看不到任何进度和 `[警告]`，只有进程结束才一次性刷出来。第一轮就是这样两眼一抹黑，
   没法判断到底是在跑还是卡死了。
3. **变体数 2 张就够，不用 3。** 关键帧是"确认这一镜能不能用"，不是角色基准立绘。
   `keyframe_prompt_guide.md` 写的就是 `count` 默认 2-3。

#### 断点续跑

`build_tasks()` 用 `start_idx = len(existing)` 决定编号，**同一个 job 重复跑只会往后
接着编号（`_02`、`_03`…），不会覆盖已有文件**。所以中断之后**不要重跑整个
`jobs_ep03.json`**（已经出好的镜头会白白再出 2 张）。按下面这样生成"只含待补镜头"的清单：

```bash
python3 - <<'PY'
import json, pathlib
root = pathlib.Path("output/出狱后我成为了非洲矿王/keyframes/ep03")
jobs = json.load(open(root/"jobs_ep03.json"))
out = []
for j in jobs:
    have = len(list((root/j["id"]).glob("*.png")))
    need = max(0, 2 - have)
    if need:
        out.append(dict(j, count=need))
json.dump(out, open(root/"jobs_ep03_rest.json","w"), ensure_ascii=False, indent=2)
print("待补 job:", len(out), "| 待生成图:", sum(j["count"] for j in out))
PY
```

`jobs_ep03_rest.json` 是随时可重算的临时清单，不是需要长期保留的文件。
撞到额度重置提示（`try again at 5:56 AM` 这类）就停下，不要无脑重试。

## 第 13 步实操踩到的坑（换 Pod 必踩，记住）

**Pod**：`tt0ljasiaeahnc` / A100-SXM4-80GB / US-KS-2 / **$1.59 每小时**（列表价 $1.39 是
`lowestPrice`，实际按 `costPerHr` 收）。Network Volume `vr1dk0uvnx` 挂 `/workspace`。

### 坑 1：`uv` 不跨 Pod 持久，但 `.venv` 持久

新 Pod 上 `uv` 命令**不存在**——它装在容器盘上，容器盘不跨 Pod。
但 `/workspace/LTX-2/.venv` 在 Network Volume 上、**完好保留**（torch 2.13.0+cu132、
`ltx_pipelines` 都能直接 import）。

所以 `ltx_remote_config.json` 的 `python_bin` 从 ep02 的 `uv run python` 改成
**`.venv/bin/python`**，不必重装 uv，也不必重建环境。67GB 权重同样完好，
**整个"下载+装环境"的一小时全省掉了**。

### 坑 2：`ltx_ssh_submit.py` 的 ssh 调用不带 `StrictHostKeyChecking=no`

新 Pod 的主机密钥不在 `~/.ssh/known_hosts` 里时，脚本的 ssh 子进程**非交互式直接失败**，
报 `returned non-zero exit status 255`，3 个镜头全部 error，且**几十秒就返回**
（看起来像生成失败，实际连都没连上）。

**注意别被自己坑**：我先前手动 ssh 用的是 `-o UserKnownHostsFile=/dev/null`（用完就丢），
所以"我能连上"并不代表脚本能连上。

正确做法是在提交前把主机密钥正式写进 known_hosts：
```bash
ssh-keyscan -p <SSH端口> -H <公网IP> >> ~/.ssh/known_hosts
ssh -p <端口> root@<IP> 'echo SSH_OK'   # 不带任何 -o 参数验一次，能通才提交
```

### 坑 3：提交脚本也要 `python3 -u`

跟出图脚本同一个毛病：不加 `-u` 时日志文件一直是空的，看不到进度，
只能靠 `ps -ef` 看子进程和 ssh 上去查 `nvidia-smi` 才知道到底在不在跑。

### 一个会误判的现象

提交后头一两分钟 `nvidia-smi` 显示 **GPU 0%、显存 0 MiB**，这是正常的——
67GB 权重正在读进显存。不要据此判断"任务没跑起来"，
去看 `/workspace/jobs/` 里首帧 png 有没有上传、远程有没有 `ltx_pipelines` 进程更准。

## 改过的 skill 文件（这次修了一个真 bug）

**`.claude/skills/short-drama-ltx-export/scripts/validate_video_jobs.py`** —— 否定词扫描
现在会**先摘掉引号里的台词**再扫。

原来的实现对整条 `prompt` 做子串匹配，于是把 ep03 镜14 台词
「**能不能**找到矿，要看过岩层结构才知道。」里的「能不能」当成否定词「不能」拦下来了。
这是误报，而且是会反复发作的那种：

- 台词是**说话内容**、是剧本原文，不是给模型的指令；ledger B1 要防的是
  `避免XX` 这类**指令**被注入文本编码器。
- 中文否定词按子串匹配，正常台词踩雷的概率很高——「我**不能**答应你」「**没有**别的办法」
  「你**不要**逼我」都是短剧里再常见不过的句子。
- 镜14 还是 S 级镜，整场戏的重点恰恰就在这句"他不打包票"上，改台词等于把戏改没了。

改法（`validate_video_jobs.py` 否定句检查处）：
```python
scan_text = re.sub(r'"[^"]*"|“[^”]*”', " ", prompt_text)   # 摘掉台词引号
negations = bp.find_negations(scan_text)
```
en 模式的台词用 ASCII 双引号、zh 模式用中文引号，两种都摘。

**已做回归验证**：往 prompt 里塞一句真的指令式否定「避免出现字幕和水印。」，
仍然被正常拦下报 ERROR。只有引号内的台词被放行。
