# 四个以上 subagent 的调度

人数及职责以 [../SKILL.md](../SKILL.md) 为准。最多四个 active unit 是任务队列
上限，不等于可以同时启动八个代理；宿主实际允许的代理数和图像调用数分别计量。

## 开始前

1. 读已批准范围、队列历史和已生成文件，继承轮次与验收。只编辑 skill 时不执行此调度。
2. 查询当前代理槽位和完成代理是否会释放槽位，记录宿主真实返回的信息。
   不将 idle／interrupt 等同于已关闭或槽位已释放；仅使用宿主实际提供的生命周期操作。
3. 至少两个可生成 unit 时分配 G1、G2、R1、R2；只有一个时分配 G1、R1、R2、R3。
   每个名字必须对应不同的真实 agent ID，并有实际产物。只启动后闲置不算参与。
   即使依赖只允许先生成一张，也可按单 unit 配置先启动完整流程，后续再加入生成者。

## 宿主只有三个子代理运行槽位的例子

- G1 与 G2 分别生成不同 unit；任一图片落盘且有空位，即可让 R1 看图。
- G1/G2 完成后，等待宿主回收或用它支持的关闭操作释放槽位，再创建独立 R2。
  R2 实际打开拟选图、相关候选及前后镜头参考，做连续性检查。
- G1、G2、R1、R2 是累计四个不同的代理，峰值不超过三个同时运行的子代理。
  如果完成代理仍占总名额且无释放能力，不能假定后面能创建 R2；报告未满足四人条件。
- 单 unit 依次使用 G1 与 R1/R2/R3；三名审查者看同一轮图片，不额外调用图像生成。

## 流水线

将最多四个依赖已满足的 unit 标为 active；为每个 unit 只安排一个 Generator
写入其目录，同一 unit 的下一轮必须等上一轮所有审查意见合并后才能启动。
不必等整批生成完才开始审查；有可执行任务和空槽位就推进。

R1 对每张新候选给出单图判断，R2 对拟选图独立做连续性与参考一致性检查；
单 unit 模式另由 R3 独立复核。R2/R3 先形成自己的看图观察，再核对其他意见，
不能仅背书已有结论。任何审查未通过或尚未完成，unit 都不能标为 passed。
每场的所有图还须一起看一次；跨镜问题退回受影响的 unit，不随意改写原剧本。

主代理合并每轮 verdict：全部通过才写 selected_file；未通过且少于三轮则按
字段反馈改源卡、重新装配，生成下一轮的2或3张。每名代理职责固定，不把旧
Generator 重新命名为 Reviewer；可复用同一职责的代理，但复用不增加不同代理计数。

三轮到限标为 capped，selected_file 为空、best_candidate 仅供查看；停止该 unit，
汇报差异，腾出槽位推进独立任务。依赖其主帧的镜头标记 blocked_dependency。
重启工作流不清零轮次。缺图、限流及调用错误如实落盘，不能伪造成已完成生成／审查。

只由主代理合并 units_queue.json、agent_roster.json、selected.md/keyframes.md
及共享 manifest；子代理写自己的任务目录和审查报告，避免并发覆盖公共文件。
现有生成脚本若会写 manifest，给各 Generator 独立输出目录，结束后再合并。

达到宿主限流时减少同时运行的任务，不减少必须实际参与的独立代理总数。
结束时核对至少四个真实 ID 各有实际交付物，且每张选图的生成者和审查者不同。
