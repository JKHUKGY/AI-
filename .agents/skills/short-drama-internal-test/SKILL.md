# 内部全流程测试

本 skill 负责串联现有技能、保存断点、落实用户确认和汇总测试结果，不复制各环节的生成规则。
只编写或修改本 skill 不代表执行测试。被要求运行时，从输入准备开始推进到最近的未获准关口。

## 路径与测试范围

- 从仓库根运行；同级技能根 `S`：Codex 用 `.agents/skills/`，Claude 用 `.claude/skills/`。文中的 `S` 是路径占位符，执行前替换。只读当前阶段需要的 skill 与引用资料。
- 用户指定剧目、集数、镜号、模型时沿用。未指定时新建 `output/_internal_test_<时间戳>/`，使用原创微型故事：一个场景、至多两个角色、ep01 三个相邻镜头。默认视频通道 LTX；用户选择 H3 时使用 H3 自建通道。
- “全流程”默认覆盖所有制作阶段，不扩展成全剧生产。复用项目只读取用户指定范围；新测试产物写入独立目录，不覆盖正式剧目。复用阶段标为 `reused`，不能冒充本轮实测生成。
- 初始化 `_test/run.json` 和 `_test/report.md`，结构见 [运行记录](references/run-record.md)。沿用标准 `storyboard/`、`assets/`、`keyframes/ep01/`、`videos/ep01/`，测试资料放 `_test/`。
- 遵守根 `AGENTS.md` 的写入边界；临时文件和缓存放项目内 `tmp/`。本 skill 不改变沙盒、审批配置或可写目录。系统免审批配置不代表用户批准了生成。

## 两类必停关口

**每批实际调用图像生成前走 G1；每批租用/启动 GPU 或提交视频生成前走 G2。**
关口是可重复进入的两种类型，不是全程仅暂停两次。人物/场景图、场次主帧、逐镜关键帧可能分属不同批次。

第一次到达关口时必须：准备可审阅文件 → 按 [确认协议](references/confirmation-gates.md) 展示具体方案 → 记录 `waiting_user` → 结束当前轮回复，等待用户回答。
未经确认，主代理、subagent、脚本、后台任务都不得执行受关口控制的动作。不能边提问边启动任务，也不能先出一张、先租卡或先建收费存储来“验证”。
只有用户针对已展示批次的明确同意才能继续。已有的同批有效确认可以沿用；“测一下全流程”、过去对另一批的同意、工具审批通过、`approval_policy = never`、超时和 AI 自填的 `approved` 都不能代替确认。

## 按依赖推进

| 阶段 | 调用/读取的同级 skill | 完成条件与下一步 |
|---|---|---|
| 0. 输入及计划 | 已知路径直接读；定位才用 `index` | 保存测试范围、原始故事来源、项目内输出路径及待测阶段。只做只读环境检查，不自动登录、安装全局依赖或操作云资源。 |
| 1. 故事 | `short-drama-scout` | 没有故事则按测试范围原创，保存独立剧本/对白原文与梗概；已有剧本直接引用。后续审查以此为事实来源。 |
| 2. 分镜及设定 | `short-drama-storyboard` | 产出 `style_bible.md`、`characters.md`、`scenes.md` 和范围内 `ep01.md`；逐镜保留剧本原文锚点、机位、动作、台词。 |
| 3. 素材任务准备 | `short-drama-image-gen` 的输入与 jobs 装配部分 | 形成角色三视图、场景机位任务及提示词，列清参考图和张数；到 **G1（素材批次）停下**。此时不执行生成部分。 |
| 4. 素材生成与审查 | `short-drama-image-gen` + `loop-picture-generation` | G1 有效后实际生成、独立审图；通过项登记 `assets/selected.md`，到限项记录失败，阻塞其依赖。 |
| 5. 关键帧任务准备 | `short-drama-keyframe-gen` 阶段一 | 使用已选素材填 `scene_beats`、关键帧卡，机械装配主帧/逐镜提示词与审阅表；到 **G1（主帧/关键帧批次）停下**。同时履行该 skill 的走位确认。 |
| 6. 关键帧生成与审查 | `short-drama-keyframe-gen` 阶段二 + `loop-picture-generation` | 按依赖先生成获准主帧，再生成获准逐镜图；记录 `keyframes.md` 及场次连戏审查。若后续批次尚不能给出真实参考图和具体提示词，则先完成依赖，再单独提交该批 G1。 |
| 7. 视频镜头卡 | `short-drama-video-gen` | 实际看首帧，填写 `shot_cards.json`；保留原剧本 `script_ref`，装配 LTX `video_jobs.json` 或 H3 `h3_jobs.json`。 |
| 8. 提交前准备 | LTX：`short-drama-ltx-export`；H3：`minimax-h3-export` | 完成本地装配、路径/规格/语言/预算校验，准备远端配置与费用方案；到 **G2（租卡及视频批次）停下**。尚无 Pod 时不能为补 SSH 地址先租卡，详见确认协议。 |
| 9. 租卡与视频生成 | 对应 `short-drama-ltx-generate` 或 `minimax-h3-generate`，生成审查用 `loop-video-generation` | G2 有效后租卡/部署、补全真实远端配置并完成 dry-run，再按批准镜头串行试跑与生成。H3 使用其提交器和音频审查，不能套用 LTX 的命令。 |
| 10. 收尾与报告 | 对应生成 skill 的关机机制；本地 ffmpeg（可用时） | 下载结果、抽帧/听审、拼接已通过镜头的测试预览；确认本批 GPU 已停止计费并登记存储费用；汇总 `_test/report.md`。不自动发布网站、上传成片或更新正式站。 |

关键帧与视频提示词都由卡装配，返工先改卡再装配，不手改派生 prompt。
上下游已有的人工作品审阅要求继续有效；准备阶段自动推进，不为普通文本步骤额外发明确认关口。

## 审查、失败与断点续跑

- 每个获准出图批次按 `loop-picture-generation` 配置至少四个真实、不同的 subagent（主代理不计入）；按宿主槽位分批，记录真实 ID。缺乏此能力时标记阻塞，不能用同一代理换角色代替。
- 图片每 unit 按 1→2→3 张、最多三轮；使用用户批准的更小上限时服从该上限。继承已有轮次；`capped` 不能登记为通过，依赖失败素材的后续任务不生成。
- 视频遵守 `loop-video-generation` 的 L1/L2/L3 路由和已批准重试/费用上限。L2 需要重出图时回 G1；L3 改分镜停下交给用户。后续视频若超出原 G2 的范围/预算，重新走 G2。
- 等待新的用户确认前，如本批仍占用计费 GPU，先按已批准收尾方案释放本批资源并核实状态，再等待。不要让显卡空转等回复，也不要操作其他任务的实例。
- 中断、失败或到达预算上限，停止新提交，优先收尾本批 GPU；收尾失败明确标记 `cleanup_pending`，报告具体资源和状态，不声称已停止计费。
- 恢复时先读 `run.json` 与当前待审方案，再核对文件、真实任务状态、用户确认来源和剩余轮次；缺少确认证据就停在对应关口，不根据文件存在推断授权或通过。
- 最终结论区分 `passed` / `partial` / `blocked` / `failed`：全部测试范围、独立审查和收尾证据齐全才算通过；只产提示词、只 dry-run、复用结果或未实际生成不能称为整链路实测通过。

调用示例：`用 short-drama-internal-test 做一次三镜内部联调，在出图和租卡前等我确认。`
