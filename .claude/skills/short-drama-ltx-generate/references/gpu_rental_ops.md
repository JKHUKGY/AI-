# 租显卡跑 LTX-2.5：实操注意事项（以 vast.ai 为例，2026-08 实测）

这些是实际操作云端显卡租赁时踩过的坑，不是理论建议。用户提供了平台的
API key 之后，Claude 应该能通过对应 CLI/API 自己完成这些操作，不需要
用户手动点网页——但要按下面的顺序检查，不要一上来就租卡。

## 0. 选卡之前先确认显存够不够

LTX-2.5 权重合计约 66GiB。选卡门槛：

- **显存 ≥ 80GB**（比如 A100-80G、H100、RTX PRO 6000 系列 96GB）：可以
  完整精度直接跑，不用量化/offload，本仓库实测用的是 96GB 卡。
- **显存 32-48GB**：需要 `--quantization fp8-cast --offload cpu/disk`
  才可能跑起来，会明显变慢，且不保证一定能塞下——**不要一开始就假设
  "显存足够"，去查实例页面上显示的 GPU 型号和显存数字确认**，不要相信
  用户口头说的"应该够"（本仓库真实发生过用户说"显存足够"，实测是 32GB
  消费卡，装不下完整模型的情况）。
- 磁盘空间：模型权重 66GB + 系统/依赖，建议实例磁盘 ≥ 150GB。

## 1. 账户/计费状态，租卡前先查

用类似 `vastai show user --raw` 的接口查账户状态，重点看：

- `balance`（真实预存余额）和 `credit`（赠送/推荐额度）是两回事，`credit`
  不为零不代表能正常起实例。
- `has_billing`（是否绑定了支付方式）、`is_subject_to_unpaid_deletion`
  （账户是否被标记欠费）。
- **症状识别**：如果启动实例反复出现"排队后请求资源不可用"、状态在
  `actual_status=loading`/`cur_state=stopped` 之间反复横跳、换了好几个
  不同的 offer/地区都是同样的表现——很可能是账户计费问题（没绑定支付
  方式），不是显卡本身的问题。这种情况下应该先提醒用户去平台网页绑定
  支付方式，而不是一直换显卡重试浪费时间。
- 但如果**换一个 offer 立刻正常启动**，说明只是那个具体宿主机的问题
  （本仓库真实发生过：同一账户先后 3 个 offer 里，前两个反复起不来，
  换到第三个直接正常跑通），不是账户层面的问题，不要误判成计费问题。

## 2. 实例状态字段不可信任一次查询结果

`actual_status`/`cur_state`/`intended_status` 这几个字段有时会互相矛盾
（比如 `status_msg` 显示"success, running..."但 `cur_state` 是
`stopped`），说明状态还在收敛中。正确做法：

- 轮询而不是查一次就下结论，间隔 10-15 秒，给足够时间。
- 用后台轮询（长跑的 bash 任务）而不是前台傻等，避免占用会话。
- **实例可能在正常运行一段时间后自己意外停止**（本仓库真实发生过：
  已经成功生成了 10 个视频片段后，实例自己变成 `stopped`，且无法
  `start` 回来，反复尝试都是"排队"后又变回停止）。遇到这种情况，
  重试 1-2 次仍不行就直接销毁重建，不要在一个坏掉的宿主机上死等。

## 3. 换显卡/重建实例的操作顺序

1. 确认新 offer 的显存/价格/地区/可靠性（`reliability2`）/磁盘空间。
2. 销毁卡住或不再需要的旧实例（`vastai destroy instance <id> -y`），
   避免同时计费或占用账户实例数配额。
3. 创建新实例时的 `--image`：**优先用第 3.5 条的自制"预装好"镜像**（如果
   已经存过快照），没有的话退回用基础镜像（比如
   `pytorch/pytorch:2.4.0-cuda12.4-cudnn9-devel`，带 CUDA devel 工具链）。
   `--ssh --direct` 开直连 SSH，磁盘按上面第 0 条给够。
4. 如果这次是从基础镜像起步，新实例需要重新走一遍环境搭建（clone 仓库、
   装 uv、下模型权重），这些步骤本身很快（uv sync 几分钟、67GB 模型下载
   在高带宽机器上 1-2 分钟），不是大成本，换卡不用太犹豫；但如果换卡
   次数已经不是第一次，应该主动提醒用户"要不要把当前这台存成镜像，下次
   直接复用"，而不是每次都重新装一遍。

## 3.5 存镜像，下次换卡不用重新下载（`vastai take snapshot`）

环境搭建（clone + `uv sync` + 下载 66GB+ 模型权重）本身不算贵，但**换卡
换太多次会累积成明显的时间和流量成本**。vast.ai 支持把一个已经配置好的
容器打包成 Docker 镜像推送到镜像仓库，下次创建实例直接用这个镜像做
`--image`，容器一启动所有依赖、仓库代码、模型权重就都在里面，不需要重新
走第 2 步的环境搭建。

```bash
vastai take snapshot <实例ID> \
  --repo <用户的镜像仓库地址，比如 someuser/ltx2-ready:v1> \
  --docker_login_user <镜像仓库用户名> \
  --docker_login_pass <镜像仓库密码或 access token> \
  [--container_registry docker.io]   # 默认就是 docker.io（Docker Hub），
                                      # 也可以是 ghcr.io 等其他 registry
  [--pause true]                     # 默认 true：先暂停容器再打包，更安全
                                      # 但慢一些；false 更快但可能拍到
                                      # "正在写文件"的不一致状态
```

**这需要用户提供镜像仓库账号的凭证**（Docker Hub 用户名+密码/token，或者
其他 registry 的等价物），不是 vast.ai 自己的 API key 能顶替的，第一次用
之前要问用户要。

**什么时候值得存镜像**：
- 已经反复因为宿主机不稳定换过好几次显卡（本仓库真实发生过连续 3 台
  实例才租到一台能用的），说明"重新装环境"这件事发生频率不低。
- 模型权重版本没有变化、后续还要继续用同一个 pipeline 配置。

**什么时候不值得**：
- 只是临时用一次、不打算长期维护这条生成通道。
- 镜像仓库大小/带宽限制可能扛不住 60GB+ 的镜像（免费版 Docker Hub 对
  超大镜像的推送/拉取速度和额度需要用户自己核实，不要替用户假设"肯定
  没问题"）。

**存好之后怎么用**：下次 `vastai create instance <offer_id> --image
<用户的仓库>:<tag> --ssh --direct`，跳过第 2 步的 clone/uv sync/模型下载，
直接 SSH 进去确认路径没变（模型权重路径、仓库目录）就能跑生成，只需要
重新装看门狗（第 1 步第 5 条）——看门狗不是镜像的一部分，每次新实例都要
重新启动它。

## 4. 成本管理

- **用完就关是默认行为，不用问用户**：这一批任务跑完、结果都下载到本地了，
  立刻跑
  ```bash
  python3 .claude/skills/short-drama-ltx-generate/scripts/gpu_teardown.py \
    --config output/<故事名>/videos/ep0X/ltx_remote_config.json
  ```
  （config 里要有 `platform: "vast"` + `instance_id`）。它会 `vastai stop
  instance` 并**轮询 `show instance` 确认 `actual_status` 真的变了**——
  vast.ai 上"接口返回成功但实例还在排队/还在跑"是踩过的坑，所以不确认
  不算关成功。验收（抽帧、看图、写汇报）都是本地工作，不需要实例在线。
  更省事的是提交时就加 `ltx_ssh_submit.py --auto-stop`，跑完自动关。
  **vast.ai 上 `gpu_teardown.py` 只做停机、不做销毁**（`vastai destroy
  instance` 会连盘上的 67GB 权重一起删，要用户明确说"这台不要了"才手动做）。
- **实例一启动就自动带上闲置看门狗**（`scripts/idle_shutdown_watchdog.py`，
  见 `SKILL.md` 第 1 步第 5 条），这是标准步骤，不是可选项——连续 2 分钟
  检测不到 GPU 利用率或生成进程，就自动停止实例，不需要用户手动提醒或
  等 Claude 想起来才去停。
- 看门狗是兜底，**不能拿它代替上面那一步主动关机**：干等它超时的那 2 分钟
  一样在计费，而且它依赖当前会话存活、SSH 连通性等条件，不是 100% 保证
  （会话一关它就没了）。汇报里要写清楚显卡现在是关了还是还开着，不要假设
  看门狗一定会按预期触发就什么都不说。
- 如果用户明确说马上还要继续用这台显卡（比如紧接着要跑下一批任务、或者
  要手动测试 `--help`），提醒用户看门狗还在盯着，只要中途没有生成进程/
  GPU 利用率超过 2 分钟就会被自动停掉，问清楚要不要先把看门狗停掉
  （直接 kill 那个后台进程）再进行长时间的非生成类操作。
- 每次批量提交任务前，粗略心算一下预计耗时和费用（单镜生成实测大约
  1 分钟量级，10 镜批量提交实测几分钟内跑完），让用户对成本有数，不要
  闷头跑一个可能要很久的批次。
