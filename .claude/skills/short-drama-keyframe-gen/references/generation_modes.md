# 关键帧的两种出图模式

本规范用于场次主帧和逐镜关键帧。复用 loop-picture-generation 的独立人员和实际工具调度；本规范明确覆盖其旧版“fail立即自动重出”“每轮必须凑满1/2/3张”“失败图一律不能选择”的决策规则。角色和场景基准图不随之改变。

## 模式选择与授权

|模式|决定是否返工|适用|
|---|---|---|
|`managed` 完全托管|在用户批准的范围和预算内，代理依据严格审查自动修正|愿意等更久，希望自动完成严格筛选|
|`user_choice` 用户选择|代理展示图片、独立反馈和推荐方案，用户决定采用或修改|网站默认，边看边决定是否继续投入|

两模式共用同一质量标准，区别是返工决策权。不能把用户选择模式做成只出图不审查，也不能把托管理解成无限追求像素一致。

持久化模式及来源，优先使用当前明确选择、已有项目／批次设置。新任务未指定时用 `user_choice`；“自动修到好／全托管”属于 `managed`。已有批次未记录模式时依据其批准记录迁移，不因 skill 更新重问、切模式或重置次数。模式切换只影响未提交的工作，不改历史和已发生调用。

首次出图批准与返工决定分开。用户选择模式中，“生成这一批”只授权列出的首轮或已展示方案；没回复不等于批准下一轮。选择托管后，不为授权范围内的每次修复再次请求确认。改变原文、角色设定或批准走位的实质设计变更仍须展示，不能伪装成修图。

## 每张图的交付顺序

生成并落盘 → 立即展示“已出图，审查中” → R1逐图看、R2按后述分工独立看拟选／修正依据／分歧图 → 合并推荐图和最小修正方案 → 按模式选图或修正。单镜起始批次另完成R3；最终选图必须审查齐全。

不等整轮／整集才展示。审查未齐时用户可以预选；最终采用要等必需独立审查完成。若审查新发现主要问题，保留预选并展示差异，由用户确认是否接受，不能替用户勾选。已有明确“到限都替我选最佳”的授权可直接执行并记录来源。

每次反馈给用户四项：

1. 推荐图片和一句理由。
2. 最影响本镜的1–3个问题及其影响，小问题折叠。
3. 一份推荐修正：基于哪张、只改哪里、保留什么、将新增几张，以及可能的退化。
4. **采用这张**／**按推荐修改**；另提供“自己描述修改”和“稍后决定”。不要要求用户阅读原始 prompt 或逐条审批技术清单。

## managed：严格自动筛选

- 同一候选取得全部必需 Reviewer 的 pass 后立即选定；minor 提醒不触发自动重画。
- 有有证据的 major／critical 缺陷，并且有针对性的修正方案，才自动执行。先改源卡／关联编辑计划，再机械装配。
- 每轮先提交一张；通过就停，失败再依据证据决定追加同方案候选或进入下一方案，不能为凑数原样盲试。
- **无改进停止**：连续两次已审修改都没有缓解目标缺陷，或最新修改反而引入更严重的身份／动作／材质退化，标 `needs_decision` 并保留最佳候选。没有合理新方案时提前停，严格不等于必须用完六张。
- 第三轮候选额度耗尽仍失败，标capped并停止。已有到限择优授权时选最佳并记录原fail；否则展示最佳图和差异等待用户。其他独立已授权镜继续。
- **提前停不等于到限**：还有已允许额度但因无改进／退化暂停，标needs_decision；仅有“到限替我选”授权时，不能擅自延伸到提前停止。除非用户另有“任何停止时都选最佳”等明确策略，否则新增调用为0、保留推荐但不最终选定。到限以第三轮允许候选额度耗尽或用户明确设置的更小限额耗尽为准。

## user_choice：先展示，再决定

- 已批准范围内每镜先一张。某镜等待用户不阻塞其他独立镜的首轮。
- 独立反馈齐后进入 `awaiting_user`，此镜不自动提交下一轮；释放运行槽位，只保留持久待办。
- **采用这张**：合格图记录用户选择；有缺陷图一次展示会带入下游的问题，用户确认后保存 `selected_by_user`，原技术 fail 不改，不再重复请求同一确认。
- **按推荐修改**：只执行用户看到的方案版本，默认先一张。出图与审查后回到选择面板，不顺带跑完剩余轮次、改其他镜或全项目托管。
- **再试一张**：保持同方案及源卡哈希，只用本轮余量；**改变修正方案**：新快照进入下一轮。
- 支持多镜批量接受各自推荐修改，但必须展示镜号、方案版本和总新增预算；一次点击不能被解释为无限自动返工。
- 用户采用后，取消未提交的修改计划；已经在途的图片归档为候选，不能迟到后覆盖用户选图。

## 轮次、预算和抢先停止

新任务把旧 `1→2→3` 改为每轮**最多**1／2／3张，总上限仍为三轮、六张。明确要求固定张数的任务依其授权执行；已运行批次不追溯改计数。

第1轮是初始已批准方案，第2／3轮是依据反馈改过的源卡或编辑计划。轮内候选共用源卡、计划和 prompt 快照。轮次在该轮第一次**提交**时登记，不能等整轮审查结束才计数，防止重启重复调用。失败后不改方案只换随机结果属于同轮余量，不是重置预算。

`round_limit`、本次 `requested_count`、`submitted_count`、`generated_count`、`reviewed_count`、未提交取消数分别记录。默认一镜最多一个图像调用在途；每次用户只同意一张时，不把本轮上限2／3直接传成批量脚本 count。

全部通过、用户采用或用户停止后，取消未提交余量，不为了人数或轮次凑图。已在途调用按宿主支持取消或等待归档；无法取消时如实说明可能仍返回图片。成功返回的图保留来源并完成所需审查；选图版本不能被旧任务回写覆盖。

技术失败实际产图为0，单列错误。瞬时错误有限恢复；相同拦截／错误反复出现就停该镜，不能无限重试、绕审核或重跑整轮。续跑先核对提交记录、工具返回和目录，缓存丢失不是重新生成的理由。

## 四名代理和流水线

批次至少四个不同真实 subagent；主代理不计数。通常 G1/G2 分镜生成，R1 单图、R2 连戏；批次起初只有一镜时使用1G+3R。多镜批次收尾只剩一镜，沿用原角色，不新增批次、代理人数或轮次。

R1实际审每张新候选；R2优先独立审每镜拟选图、修改方案所依据的最佳候选和有分歧的图。R1已明确淘汰且未进入推荐的其他图可只保留单审，标明审查范围；用户后来选中它时再补R2。每张最终选图必须完成全部必需独立审查，单镜起始批次还需R3；技术通过仍要求同一图全部pass。下一修正方案要等其依据候选的独立反馈齐全，不凭一个人的主观偏好直接反复重画。

各Reviewer先独立观察再合并，Generator不自审。主代理不重复做第三遍全量审查，只对实际选图取舍或分歧查看必要图片。四人是累计参与，不要求同时运行。运行代理数、在途图像调用数分别服从宿主限制。

最多四个依赖已满足的 active unit。优先让新的独立镜出首轮，而不是被一个难镜占住整批；当反馈齐、模式允许返工时再排修正。等待用户的 unit 不占 active 配额。数据落盘即唤起可用审查者，不攒批；不要让审查者常驻等待尚未出现的图。

相同 Reviewer 可复用自己已实看的未变参考和已确认上下文，按图片哈希、设计版本和依赖版本判断是否失效。每个新候选仍检查目标改动、保留项和可见退化。整场选完查一次；之后换一镜，只复核该镜及受影响相邻关系。工具耗时、排队、审查耗时、用户等待分别记账，不能把总等待都称为模型生成慢。

## 状态与选图：两个事实分开

|字段|含义|
|---|---|
|`workflow_mode` / `mode_version`|返工决策模式及其版本|
|`generation_state`|queued / generating / reviewing / awaiting_user / needs_decision / done / stopped / technical_error|
|`review_status`|pending / passed / failed；始终来源于独立报告|
|`selection_status`|unselected / preselected / selected / selected_by_user|
|`selected_file` / `selection_version`|已选择的真实候选及选择版本；允许用户明确采用failed图|
|`known_issues` / `selection_basis`|剩余问题和用户采用／自动通过／已有择优授权依据|
|`rounds[]`|方案快照、调用与产图计数、错误、所有独立报告路径|
|`proposals[]` / `decisions[]`|反馈方案与用户决定的版本、对象、时间和执行状态|
|`scene_review_status`|pending / complete_with_issues / passed；与逐镜选择分开|

旧队列可继续用 `status` 兼容字段，但不能据它覆盖上述事实。选图不等于技术通过，主帧推荐不等于主帧已选。用户采用有问题主帧时，展示一次其对下游的影响，确认后允许依赖使用并传递 known_issues。未审完或尚未选定的主帧不解除依赖。

## 本轮完成的定义

托管：授权镜均已选、到限／技术停机／需要设计决定等已明确分类，且审查与整场记录完整。
用户选择：本批候选与独立反馈已交付即可结束计算，待决定镜持久保留；不要把它们说成“已完成选图”。所有镜选定且整场复核记录完成后，才说本集选图完成。
