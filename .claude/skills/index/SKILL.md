# 仓库定位入口 (index)

这个 skill 不产出任何东西，只回答"在哪 / 到哪一步了"。目的是让你**读三份文档
就能定位**，而不是对着 400+ 个产出文件做全仓库搜索。

## 怎么用（按问题类型走，不要三份全读）

| 用户在问什么 | 读哪份 |
|---|---|
| 某个**文件/目录/脚本/规则**在哪、某个 skill 管哪一步、产出目录怎么组织 | `INDEX.md`（仓库根） |
| **网址、登录账号、云主机、API key、租显卡平台、原始剧本 docx** 在哪 | `references/resources.md` |
| **现在做到哪一步了**、哪部剧做了几集、还差什么 | 跑 `scripts/snapshot.py`，别靠记忆也别信文档里的进度数字 |
| **上次为什么这么做**、历史决策 | `需求.md` 里按日期追加的"AI 已做"日志（最新一条在最下面） |
| 提示词/分镜**方法论**为什么是这样 | `研究.md`（skill 里的硬规则大多出自这里） |

```bash
python3 .claude/skills/index/scripts/snapshot.py              # 全部剧的实时进度
python3 .claude/skills/index/scripts/snapshot.py --project 暗局
python3 .claude/skills/index/scripts/snapshot.py --online     # 顺便探测线上网站活没活
```

## 三条硬规则

1. **磁盘和线上状态优先于文档。** `INDEX.md` / `resources.md` 是手写的，可能落后于
   现实。凡是要给用户一个"数字"（做了几集、几张图）或"值"（网址、IP、状态），
   先跑 `snapshot.py` 或对应的验证命令（`az vm list -d -o table`、`curl` 探活），
   再回答。
2. **找不到就先读地图，再搜。** 连着两次 grep/find 没命中，停下来读 `INDEX.md`
   对应那一节；很多东西不在仓库里（账号、key、显卡配置按设计就 gitignore 了，
   见 `resources.md`），继续搜只是浪费。
3. **发现地图错了当场修。** 新增一部剧、改了目录结构、换了网址或机器、加了新
   skill——顺手改 `INDEX.md` 或 `resources.md` 对应那一行，别留给下一次。

## 一分钟仓库全貌

- 这是一套 **AI 短剧全流水线**：选题 → 分镜 → 人物/场景出图 → 关键帧 → 镜头卡/
  视频提示词 → LTX 校验 → 租显卡实际生成，每一环一个 skill，都在 `.claude/skills/`。
- 每部剧的产出固定落在 `output/<剧名>/`，五个子目录：`storyboard/`（分镜表和设定档）、
  `assets/`（人物三视图/表情/场景图）、`keyframes/ep0X/`、`videos/ep0X/`、
  `_web_state/`（剧本家在网站上提的意见）。
- `web/` 是给剧本家看产出、提意见、一键重新生成图片的协作网站；线上正式站的网址和
  账号在 `references/resources.md` 第 1 节。
- 贯穿全流水线的一条设计原则：**提示词是派生产物**——人只维护结构化的卡
  （`keyframe_cards.json` / `shot_cards.json`），提示词由 `build_*.py` 机械装配，
  不手写、不手改。要改提示词，去改卡再重跑脚本。
